# 中枢值守设计说明

> 公开版说明：本文是中枢值守服务（`hub/bridge-hub.py`）的设计要点，
> 从一份具体部署的实施方案提炼而来，不含任何实际部署的机器信息。

## 它解决什么

文件信箱本身只是目录：没人值守时，新信落盘了也没人知道、未读状态
没人维护、超时未读没人提醒。中枢值守就是桥上的值班员，只做四件事：

1. **感知**：inotify 实时盯信箱目录变化（新信落盘约 2 秒登记），
   外加每 300 秒全量对账一遍——文件目录是唯一真相，进程重启、
   事件丢失都靠对账补回来。
2. **台账**：未读台账存独立的 SQLite（放在只有 root 能读的目录，
   绝不放在信箱树里——信箱树对桥的 SFTP 身份是可写的，台账放进去
   等于让成员能改自己的已读状态）。
3. **清单**：按成员生成未读清单 `status/hub-unread-<成员>.json`
   （原子写：临时文件 + 改名），成员侧只读这一个文件就知道自己
   有几封未读、分别是什么。
4. **通知**：经群聊层（ntfy）发一条通知，标题 = 信件的中文
   `subject`，正文一行是文件名形式的阅读页链接；成功标准是
   HTTP 200 且返回消息对象——ntfy 对错误也回 JSON，只看状态码
   会误判。未读满 24 小时的信，每封补发一次群提醒。

## 纪律

- 中枢**从不改信件本体**：只读信件头、写台账、写清单、发通知。
  渲染阅读页是独立脚本的事，中枢只触发它（仓库附了参考实现 `hub/bridge-render.py`，部署时放到中枢配置的 RENDER_SH 路径，或换用更完整的 Markdown 引擎）。
- 回滚 = 停掉中枢服务，仅此而已；信箱、台账、清单都还在，
  成员退化为自己轮询信箱，不丢任何东西。
- 配置与启停：`hub.conf` 里两个开关（notify / render）分别控制
  发通知与触发渲染，排障时可单关一项。
- 中枢与成员的契约见 `sentinel/PROTOCOL.md`（清单格式、状态文件、
  心跳格式）。

## 已知边界

中枢是单点：它和桥在同一台 VPS 上，机器停机则全桥暂停（信件不丢，
恢复后按台账继续）。当前形态接受这个单点；真要冗余是另开一台
机器的事。
